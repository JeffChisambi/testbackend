This document outlines the architecture, database schema, API design, and development instructions for building a robust, production-ready Express.js backend for the Grain Traceability Management System (GTMS) Flutter application.

1. Architecture Overview
Since the GTMS Flutter app is designed with offline-first capabilities (evidenced by the SyncStatus entity and local SQLite usage), the backend must be designed to handle data synchronization, conflict resolution, and secure data storage.

Tech Stack
Framework: Express.js (Node.js)
Database: PostgreSQL (Recommended for relational integrity of transactions and traceability)
ORM: Prisma or TypeORM (Prisma is highly recommended for type safety and fast development)
Authentication: JSON Web Tokens (JWT)
Validation: Zod or Joi
File Storage: AWS S3 or Google Cloud Storage (for potential receipt or profile image uploads)
Deployment: Docker, deployed to AWS/GCP/DigitalOcean

3. API Endpoint Design (RESTful)
All endpoints (except login) must be protected with a JWT authentication middleware.

Authentication
POST /api/auth/login - Authenticate user, returns JWT and user profile.
POST /api/auth/refresh - Refresh JWT token.
Farmers
GET /api/farmers - Fetch farmers (Supports pagination and filtering by district/village).
GET /api/farmers/:id - Fetch single farmer details.
POST /api/farmers - Register a new farmer.
PUT /api/farmers/:id - Update farmer details.
Commodity Purchases
GET /api/purchases - Fetch purchase history.
POST /api/purchases - Record a new commodity purchase.
GET /api/purchases/receipt/:receiptNumber - Verify a purchase.
Data Synchronization (Crucial for Offline-First App)
Because field agents might work offline and sync later, we need a bulk sync endpoint.

POST /api/sync/push
Payload: JSON containing an array of locally created farmers and commodity_purchases.
Logic: The backend must handle UPSERTs (Update if exists, Insert if new) based on UUIDs generated by the mobile app. It must also deduct the loan_recovered from the farmer's seed_loan_balance within a database transaction.
GET /api/sync/pull
Query Params: ?last_sync_timestamp=1690000000
Response: All records updated or created after the provided timestamp, allowing the mobile app to update its local SQLite database efficiently.
4. Development Workflow & Instructions
Step 1: Project Setup
Initialize a new Node.js project: npm init -y
Install Express and core dependencies: npm install express cors helmet morgan dotenv
Install Prisma (Database ORM): npm install prisma --save-dev npx prisma init
Define your schema in prisma/schema.prisma mapping to the database design above.
Step 2: Implementing Security
IMPORTANT

Security is critical for a financial/traceability system.

Use Helmet.js to secure Express headers.
Use bcryptjs to hash all passwords before saving to the database. NEVER store plaintext passwords.
Use jsonwebtoken to sign access tokens with a short expiry (e.g., 15 minutes) and implement a refresh token rotation strategy.
Step 3: Handling Transactions
CAUTION

When a CommodityPurchase is synced, it often includes a loan_recovered amount.

You MUST use database transactions (e.g., $transaction in Prisma) to ensure that the purchase record is saved AND the farmer's seed_loan_balance is reduced simultaneously. If one fails, the other must roll back to prevent data corruption.
Step 4: The Sync Mechanism (Conflict Resolution)
Client-Side IDs: The Flutter app generates UUIDs for records created offline. Ensure your database accepts UUIDs as Primary Keys.
Last-Write-Wins: Add an updated_at timestamp to every table. If a record is edited on the server and on the device, compare timestamps to decide which data to keep.
Idempotency: The /api/sync/push endpoint must be idempotent. If the app sends the same purchase twice due to network drops, the backend should recognize the id or receipt_number and not duplicate the financial transaction.
Step 5: Validation & Error Handling
Use Zod middleware on your routes to validate incoming JSON payloads before they reach your controllers.
Create a global error handling middleware in Express to catch database errors and return standard JSON error responses (e.g., {"success": false, "message": "..."}).
5. Next Steps
Initialize the Repository: Create a new folder (e.g., gtms-backend) alongside your frontend.
Setup Database: Spin up a local PostgreSQL instance (using Docker or Postgres.app).
Scaffold Prisma: Write out the schema.prisma file based on section 2.
Build the Sync API: Focus first on the /api/sync/push and /api/sync/pull endpoints, as they are the primary way the Flutter app will communicate with the server.
